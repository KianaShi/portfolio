Skyscraper07 window test

portfolio / seattle backdrop
bgtest round · 2026-08-18

Single-building feasibility test: does a 3D 01_Skyscraper07 foreground mesh improve the sense of depth outside the desk-scene window, layered in front of the Seattle photo backdrop and behind the glass? Test-only — nothing here touches production.

§1

Verdict

Cautious yes

A single low-key building reads as a plausible skyline extension and adds a real (non-faked) parallax layer between the desk and the photo — but only in the L position. The R position is boxed in by the PC tower and Mt Rainier; B works but reads as a bold near-layer rather than a subtle one. Geometric detail beyond the silhouette version is invisible at this screen size, and the model needs window-light emissive before it can survive the Night state — both open items for a later round.

§4

What broke along the way

hard limit

The room shell occludes anything past z ≈ −3.87. desk-optimized.glb's Room002 mesh has an opaque face at that depth (measured at runtime, not assumed). A building placed at z=−7.5 for a "distant, subtle" look rendered byte-identical to the no-building screenshot — fully hidden. Every usable placement is confined to roughly z ∈ (−0.5, −3.7), which is a shallow corridor: apparent size has to be controlled by scale, not by pushing the model further back.

rejected

Literal window-right-edge placement fails outright. At x=2.2 (near the glass's own right bound of 2.33), the building is almost entirely hidden behind the PC tower, and the sliver that does show clips Mt Rainier's peak (screenshot below). The working R position had to move up and left, onto the only patch of sky the PC tower and Rainier don't already claim.

rejected
x=2.2, y=0.4 — clips Rainier's peak, mostly hidden behind the PC
resolved

Y=floor-level placement hides the entire building below the sill. The office is many floors up (the whole point of the skyline view), so the room's own floor height (y=−1.35) has nothing to do with what's visible through the window. Every preset's y is instead set directly against the window opening's own measured bounds (y ∈ [0.84, 3.62]).

§5

Does detail survive the screen size?

Optimized (2 materials, facade+glass) and silhouette (1 material) were captured at identical camera/position/scale. At normal viewing size they are indistinguishable — the facade/glass material split never resolves into visible windows at this distance.

Conclusion: use the silhouette variant. It costs a third of the bytes and half the draw calls of the optimized version for a visually identical result at this scale — the optimized variant's extra material/geometry budget buys nothing here.

§8

Recommendation

If you want to keep going with this building:

  1. Ship it as the silhouette variant only (§5) — the optimized variant's extra budget is invisible at this scale.
  2. Use position L. It's the only one of the three that reads as subtle scenery rather than a deliberate addition.
  3. Before any production use: give it a minimal window-light emissive pass for the Night state (§6), and consider a slight edge-soften / desaturation to close the gap between its crisp CG silhouette and the photo's soft focus — not attempted this round.
  4. Don't add a second building without re-testing crowding — even one building at L used a meaningful slice of the shallow z-corridor (§4); a second in the same window needs the same placement rigor, not a quick copy-paste.

If a subtler background is the actual goal, it's fair to conclude the photo alone was already doing the job, and this adds engineering surface (asset pipeline, emissive pass, day/night tuning) for a marginal gain. Both are reasonable calls from this data — this round's job was to make the trade-off visible, not to decide it.
